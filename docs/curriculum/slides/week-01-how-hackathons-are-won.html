01 — The plan

What this is not

we skip

Not this

Memorising syntax. Learning every framework. Typing every line by hand.

we teach

This

Using tools well: Git, AI assistants, deployment. Reading and directing code you did not write. Making product decisions fast.

AI can write a lot of the code now. The teams that win are the ones who know what to build, can check what the AI built, and can ship it before the clock runs out.

Say

  • You will not become a Python expert by January. You will become someone a team wants on it, because you can use the tools and finish things.
  • That is a different skill from knowing a language, and honestly a rarer one.

Watch for

  • Someone will ask 'so do I not need to learn to code?' Answer: you need to read it, run it, and fix it. You will do all three. You will not memorise it.

02 — What wins

What judges actually score

criterion 1

Innovation

Have I seen this before?

criterion 2

Execution

Does it work, right now?

criterion 3

Impact

Who needs this, and how badly?

criterion 4

Design

Can I use it without help?

criterion 5

Pitch

Did I understand it in 3 minutes?

Read the rubric firstNames and weights differ by event, but most hackathons score some version of these five. Judges score the product, the pitch and the potential. They rarely read the code.

Say

  • Every hackathon publishes its criteria. Reading them in the first ten minutes is the cheapest advantage you will ever get.
  • Notice what is not on the list: lines of code, how clever the algorithm is, how many technologies you used.
  • Execution is highlighted because it is the one most teams lose. A broken demo wipes out a good idea.

Do

  • Ask the room: which of these five do you think your team is naturally strong at? Which is weakest? Write two names on the board.

Watch for

  • Do not claim these are the exact criteria of the January event. Say you will check the real rubric as soon as you have it.
02 — What wins

Three ways teams lose

mistake 1

Scope too big

A half-built big idea loses to a finished small one. Judges can only score what runs.

mistake 2

Demo not ready

The pitch is rehearsed once, then the demo crashes, the Wi-Fi dies, the key has expired. Nobody had a backup.

mistake 3

No plan, no sleep

A rested team that cut scope beats an exhausted team that did not. Hour-20 mistakes are expensive.

Say

  • These three come up in almost every post-mortem. Click to reveal one at a time and ask the room if they have seen it happen.
  • Everything we do over the next eight weeks is aimed at preventing one of these three.

Do

  • Click once per card. After each, ask: has this ever happened to you in a school project?

Watch for

  • Use a school group-project example. It lands harder than a hackathon story.
What wins — quick check
Your team has 24 hours. Which plan gives you the best chance?
A deployed skeleton early means you always have something to show. Everything after that is improvement, not rescue.

Say

  • Let people vote by show of hands before you click. Most will pick B. Ask the A voters what they were thinking.

Watch for

  • C feels responsible and is a trap: a perfect backend with no interface demos as nothing.

03 — Lab

Make your GitHub account count

  1. Pick a username you will not be embarrassed by in five yearsEmployers and judges will see it. Real name or a clean handle.
  2. Turn on two-factor authenticationSettings, then Password and authentication. Use an authenticator app.
  3. Keep your email privateSettings, then Emails, then Keep my email addresses private. Commits still link to your profile.
  4. Add a profile README (optional)Create a repo named exactly like your username. Its README shows on your profile.

Say

  • Do these four in order. Two-factor is not optional: a stolen GitHub account can leak every key your team has.
  • Private email matters because commits carry an email address forever, and these repos will be public.

Do

  • Do it live on your own account on the projector while they follow. Show where each setting is.

Watch for

  • Someone will have an old account with an embarrassing username. Let them make a new one; it takes three minutes.
03 — Lab

Your first repo, your first commit

  1. On GitHub: New repository, name it hello-yourname, public, add a README
  2. Click the README, the pencil icon, write three lines about you
  3. Commit changes on the main branch, with a message
  4. Click History and find your commit
the same thing, from your machine
# now do it from your computer
$ git clone https://github.com/YOURNAME/hello-yourname.git
$ cd hello-yourname
$ code .
# edit README.md in VS Code, save
$ git add README.md
$ git commit -m "Say who I am"
$ git push

Say

  • First the website, so you see what a commit is. Then the terminal, so you see it is the same thing.
  • A commit is a saved snapshot with a message. The message should say why, not what.

Do

  • Do the website half together, step by step. Let them do the terminal half alone, and walk the room.

Watch for

  • git push may open a browser to sign in, or ask for credentials. If it asks for a password, a password will not work: GitHub removed password login for Git. Use the browser sign-in.
  • Never let anyone paste a personal access token into the group chat. If it happens, tell them to delete it on GitHub immediately.
03 — Lab

Your first AI-assisted build

a prompt with four parts: who, task, constraints, format
I'm a high school student learning web basics.
Create a single file, index.html, with the HTML and CSS inside it.
It is a personal page: my name, a one-line bio, three interests
as a list, dark blue background, light green accents.
No frameworks. After the code, explain each part in one sentence.
  1. Paste it into an AI assistant you are allowed to use
  2. Save the code as index.html, double-click to open it
  3. Change one thing yourself, reload, see it change
  4. Commit and push it to hello-yourname
The page does not matter. The loop does: ask, run, read, change, commit.

Say

  • This is the loop you will use for the next eight weeks. Ask, run it, read it, change one thing, commit.
  • The 'change one thing yourself' step is the whole lesson. It proves you can steer the code instead of only receiving it.

Do

  • If someone has no AI tool they may use yet, they can pair with someone who does. Do not let that block them.
  • Show one example on the projector, then stop talking.

Watch for

  • Some will paste the whole answer including the explanation into the file. The file only wants the code block.
  • Never paste passwords, tokens or personal details into an assistant.

Access check: what can you use?

Before you sign up for anythingMany AI tools have a minimum age, some 18 and over. Rules differ by tool and change often. Read the current terms yourself, ask a parent or teacher if you are under 18, and never share one account between people.
Tool typeWhere to lookWrite down
Chat assistantThe tool's terms, age requirementsMinimum age. Parent consent needed?
Coding assistantSame, plus the plan's student rulesFree for you? Age limit?
AI API keyDeveloper terms, not the chat app'sAllowed at your age?
GitHub student packeducation.github.comEligible with school proof?

Say

  • This is boring and important. The rules differ between tools. Some chat apps allow teenagers with a parent's permission; some do not allow under 18 at all, and the developer key sites can be stricter than the chat apps.
  • I am not going to tell you which tools you may use. I am going to ask you to check, because it is your account and your responsibility.

Do

  • Tell them you will ask the school which tools are approved, and report back in Week 2.
  • Everyone fills the table as a task, with the real minimum age they find.

Watch for

  • Do not tell anyone to use a parent's or older sibling's account to get around a limit. Do not let that become the group's workaround.
  • If a tool is out of reach for someone, they are not behind. The labs work with free tools and nothing here requires one specific product.
