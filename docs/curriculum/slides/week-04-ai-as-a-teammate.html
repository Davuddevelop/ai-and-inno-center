01 — Working with AI

Prompts that work

what most people type
# weak
make a login page
Five parts: context, task, constraints, format, check. You do not need all five every time, but you need a task and a format.
strong
I'm building a single-page web app in plain HTML, CSS
and JavaScript, no libraries.

Add a login form: email, password, a Sign in button.
Validate in the browser. Show a friendly error message.

Keep it under 80 lines.
After the code, list any assumptions you made.

Say

  • The weak prompt gets you a generic page in a framework you did not choose. The strong one tells it what stack, what to build, how big, and asks it to expose its guesses.
  • 'List any assumptions' is the cheapest trick in the whole lesson. The AI will tell you what it guessed, and the guesses are where the bugs are.

Do

  • Have everyone rewrite 'make a login page' as a strong prompt in two minutes, and read one aloud.

Watch for

  • Do not let the prompt become a long essay. Short and specific beats long and vague.
01 — Working with AI

Write the spec first

five lines, before you prompt
Feature: send button on the chat page

Done when:
1. Typing a message and pressing Send adds it to the list
2. An empty message does nothing
3. The input clears after sending
4. It works on a phone-sized screen
  • The spec is your test. When the AI says it is done, you check the four lines.
  • It also stops you asking for the wrong thing.
Paste the spec into the prompt. Ask the AI to make each line true.

Say

  • Most beginners prompt, get something, and then discover what they actually wanted. Writing four lines first is faster overall.
  • These four lines will become the PR description's 'How to test' section. You are writing the PR before the code.

Do

  • Ask the room for a feature, write the spec on the board together, then turn it into a prompt.
01 — Working with AI

Never trust, always check

  1. Does it run?
  2. Do I understand each part?
  3. What happens with empty or wrong input?
  4. Did it add a package or key I did not ask for?
  5. Does it match the spec?
AI oftenSo you
Invents functions or packagesCheck the official docs
Uses outdated syntaxRun it, read the error
Sounds sure and is wrongTest with a real case
Builds far too muchAsk for the smallest version

Say

  • These five questions are the review you do on your own code before you open the PR. A reviewer will ask the same five.
  • The invented-package problem is real: an AI will import a library that does not exist, or one that exists and does something different. Search for the package before you install it.

Do

  • Show one real failure. Ask an assistant for something slightly obscure and see if it invents a function. Even a small failure teaches more than a rule.

Watch for

  • The AI is not lying. It predicts plausible code. Plausible is not the same as correct.
01 — Working with AI

Rules for AI on our team

  • Understand every line you commit. In the demo room someone will ask how it works. 'The AI wrote it' loses.
  • AI-written code goes through a pull request, like everyone's.
  • Secrets never go into a prompt. Not keys, not passwords, not other people's personal details.
  • Say so in the PR when AI wrote most of it, so the reviewer reads it harder.
  • Check the event's own rules on AI use. Some hackathons limit it. Read them.

Say

  • These are not restrictions to slow you down. They are what lets a team use AI heavily without the project turning into code nobody understands.
  • The last one matters. Some events allow AI, some limit it, some require you to say how you used it. Find out in the first week.

02 — AI inside your product

Three patterns that win demos

AI is a feature, not the product. Name the human problem first, then ask where a model genuinely helps.

pattern 1

Answer from your data

The user asks, you look up the relevant text, you give it to the model, it answers from that. Often called RAG.

pattern 2

Turn mess into structure

Messy text, a photo or a voice note becomes clean fields: a form, a table, a schedule.

pattern 3

Draft, then edit

The model writes a first version, the user fixes it. Honest about being a draft.

Say

  • These three work because they are easy to demo in a minute and easy to explain. The best hackathon AI features are often the second one.
  • The question to ask a team: if I removed the AI, would the product still exist? If yes, the AI is a feature. If no, ask whether that is good or a gimmick.

Watch for

  • Do not push 'agents' on beginners. They are hard to make reliable in 24 hours and hard to demo safely.
02 — AI inside your product

What judges notice about AI

RiskWhat a good team does
Wrong answers shown as factsShow sources, or say it may be wrong
Real personal data in the demoUse made-up data, and say so
Bias in what it recommendsTest a few different cases before you pitch
Only one example worksTry ten. Keep the table of results
Depends on one fragile key or APIHave a saved result ready if it fails

Say

  • Judges at AI hackathons ask about these. A team that raises them first looks careful. A team that gets asked and has no answer looks like it did not think.
  • The last one is the practical one: keep a recorded or saved answer so a dead API does not kill your demo.

03 — Python as glue

Python in twenty minutes

hello.py
cities = ["Baku", "Ganja", "Sumqayıt"]   # a list

def greet(name):                    # a function
    return "Hello, " + name

for city in cities:                 # a loop
    print(greet(city))
run it
$ python hello.py
Hello, Baku
Hello, Ganja
Hello, Sumqayıt
  • Indentation is the structure. Four spaces matter.
  • An error's last line says what, the line number says where.
  • pip install name adds a package. Do it inside a project, not at random.

Say

  • This is everything you need to read the code an AI gives you: a list, a function, a loop, and how to run a file.
  • When Python errors it prints a traceback. Read from the bottom. The last line is the error, the line above it is where.

Do

  • Have everyone type the file by hand, run it, then change a city. Typing it once is worth ten reads.

Watch for

  • On Windows the command may be py hello.py. Tell them it is the same program.
03 — Python as glue

Call an API from Python

weather.py
import requests

url = "https://api.open-meteo.com/v1/forecast"
params = {"latitude": 40.41, "longitude": 49.87,
          "current": "temperature_2m"}
data = requests.get(url, params=params, timeout=10).json()
print("Baku right now:", data["current"]["temperature_2m"], "C")
  1. pip install requests (Windows: py -m pip install requests)
  2. Save as weather.py, run python weather.py
  3. Change the coordinates. Different city?
  4. Ask your AI to explain every line. Check it against the docs
FallbackNetwork blocks it? Use weather_offline.py with sample.json, run from the folder that holds both.

Say

  • An API is a web address that answers with data instead of a page. This one is free and needs no key, which is why we use it today.
  • .json() turns the answer into a Python dictionary. data["current"]["temperature_2m"] is reaching two levels in to get one number.

Do

  • Walk the room. This is where pip fails on half the machines: say 'reopen the terminal' before anything else.
  • If the school network blocks the host, the offline files are in the repo, under docs/curriculum/code/week4. Put them on the board or in the group chat.

Watch for

  • The top error: running the file from the wrong folder, so Python cannot find sample.json. Teach cd if you have to.
  • Do not hand out the finished file. They have the slide. The AI-explains-every-line step is the learning.
03 — Python as glue

The same data, as a web page

app.py
import requests
import streamlit as st

CITIES = {"Baku": (40.41, 49.87), "Ganja": (40.68, 46.36)}

st.title("Weather")
city = st.selectbox("City", list(CITIES))
lat, lon = CITIES[city]
url = "https://api.open-meteo.com/v1/forecast"
params = {"latitude": lat, "longitude": lon,
          "current": "temperature_2m"}
data = requests.get(url, params=params, timeout=10).json()
st.metric("Temperature", f'{data["current"]["temperature_2m"]} C')
then open the link it prints
$ pip install streamlit
$ streamlit run app.py
Why this mattersStreamlit turns a Python file into a web page, with widgets. It is the fastest way to put an AI or data idea in front of a judge.

Say

  • This is the first time they see their own code as a website. Give them a moment.
  • Streamlit reruns the whole file every time you touch a widget. That is why it is so simple: no page logic to write.

Do

  • Everyone runs it, changes the city list, adds a third city.

Watch for

  • pip install streamlit is large and slow on poor Wi-Fi. Start it early. If someone cannot install it, pair them up, do not stall the room.
