01 — The idea

Why version control exists

every group project, ever
essay.docx
essay_final.docx
essay_final_v2.docx
essay_FINAL_really.docx
essay_FINAL_really_Aysel_edits.docx

Now give five people one folder. Whose version wins?

the tool

Git

A tool on your computer. Saves snapshots of your project and remembers the history. Works offline.

the place

GitHub

A website that hosts Git projects. Where your team meets: issues, reviews, deploys.

Say

  • Git saves a snapshot every time you tell it to, with a message. You can go back to any snapshot, and it can combine work from many people.
  • Git is not GitHub. Git is the program on your laptop. GitHub is one website that hosts Git projects. GitLab and others exist, same idea.

Do

  • Ask who has lost work to an overwrite or a crashed file. Almost everyone has.

Watch for

  • Students mix up the two for months. Say it three times today: Git is the tool, GitHub is the place.
01 — The idea

Where your changes live

Working folderThe files you are editing right now
git add
Staging areaChanges you picked for the next snapshot
git commit
Local repositorySnapshots (commits) on your computer
git push
GitHubThe shared copy your team sees
And back againGoing the other way, git pull brings your teammates' commits from GitHub into your computer. You push what you did. You pull what they did.

Say

  • This diagram is the whole of Git for beginners. Four places, three arrows.
  • You edit files in the working folder. git add picks which changes go in the next snapshot. git commit saves the snapshot on your computer. git push sends it to GitHub.
  • Nothing is shared until you push. That is why 'it works on my machine' is a thing.

Do

  • Draw it on the whiteboard as well and leave it up all lesson. Point at it every time you run a command.

Watch for

  • The most common confusion: thinking git commit uploads to GitHub. It does not. Say that out loud.

02 — The commands

Six commands, ninety percent of the work

CommandWhat it does
git clone URLCopy a repo from GitHub to your computer, history included
git statusWhat changed? What is staged? Run it constantly
git add FILEStage a change for the next commit
git commit -m "..."Save a snapshot, with a message that says why
git pushSend your commits to GitHub
git pullFetch your teammates' commits and merge them in

Say

  • Read them down once, then say: git status is the one you run when you are confused. It tells you exactly what state you are in.
  • You do not need to memorise these today. You will have typed each of them ten times by the end of the lab.

Watch for

  • Do not teach git add . yet as a habit. It is fine, but people stage things they did not mean to. Prefer naming files while learning.
02 — The commands

Commit messages that help

Six months from now you will search this history for the one change that broke the demo. Write for that person.

unhelpful
$ git commit -m "update"
$ git commit -m "fix"
$ git commit -m "asdf"
$ git commit -m "final final"
$ git commit -m "changes"
helpful
$ git commit -m "Add login form validation"
$ git commit -m "Fix crash when the list is empty"
$ git commit -m "Move API key to .env"
$ git commit -m "Make buttons bigger on mobile"

Say

  • The rule: start with a verb, say what changed, keep it under about 60 characters. 'Add', 'Fix', 'Move', 'Remove', 'Make'.
  • In a hackathon at 3am, a clear message is the difference between finding the bug in two minutes and in forty.

Do

  • Ask the room to say what is wrong with 'final final'.
02 — The commands

Play with history

Commit. Branch. Commit. Switch back. Merge. Watch what moves.

Say

  • Give them five minutes alone with the sandbox. The questions to ask at the end: what moved when you committed? What did 'new branch' copy? What happened when you merged?
  • Answers: committing moves the branch label forward. A new branch copies nothing, it is just another label on the same commit. A merge either just slides a label (fast-forward) or makes a commit with two parents.

Do

  • Let them click. Walk the room and ask a few people to explain what they see, in their own words.

Watch for

  • Someone will make a merge commit and ask why there is no fast-forward. It is because both branches had new commits. That is the lesson, point at it.
02 — The commands

A branch is a label

  • Making a branch copies nothing. It is a new name pointing at a commit.
  • Commits move the label of the branch you are on.
  • main should always work. Do your changes on a branch.
  • Name branches for what they do: feature/login, fix/empty-list.
make one, go back
$ git switch -c feature/login
Switched to a new branch 'feature/login'
$ git switch main
Switched to branch 'main'
If you are not sure what branch you are on, run git status. The first line says.

Say

  • It is not a copy of the project. That is why branches are cheap, and why you should make one for every change.
  • The rule for hackathons: main always runs. Nobody commits half-finished work straight onto main.

Watch for

  • Older tutorials use git checkout -b. It still works. We use git switch -c because the name says what it does.

03 — Lab

Clone, branch, commit, push

git-gym, step by step
$ git clone https://github.com/ai-innovation-center/git-gym.git
$ cd git-gym
$ git switch -c add-yourname
# create students/yourname.md, three lines about you
$ git status
$ git add students/yourname.md
$ git commit -m "Add yourname to the roster"
$ git push -u origin add-yourname
  1. Accept the invitation to the repo (check your email)
  2. Do every step in order, run git status after each
  3. When it pushes, open the link Git prints and look at your branch on GitHub
-u origin add-yourname tells Git where this branch lives on GitHub. You only need it the first time.

Say

  • Everyone creates their own file with their own name. That way nobody edits the same lines, and nobody gets a conflict. Next week we will create conflicts on purpose.
  • Run git status after every step. It is your only safety net while you are learning.

Do

  • Walk the room. Look for these: someone cloning into a folder inside another repo, someone on the wrong branch, someone whose push is rejected.
  • If push asks for credentials, it should open a browser to sign in. A password will not work.

Watch for

  • If the invitation has not arrived, check the spam folder, then add them again from the repo's Settings, Collaborators.
  • Anyone who pushes to main by accident: do not panic them. It is the lab repo, it is safe. Show them how to see it.
03 — Lab

Pull what others did

Each line is a commit. The branches split off the same starting point, and you can see all of them.

see everyone's work
$ git switch main
$ git pull
$ git fetch
$ git branch -a
$ git log --oneline --graph --decorate
what it looks like
* 8c1d2fe (origin/add-aysel) Add aysel to the roster
| * 5a7e91b (HEAD -> add-yourname) Add yourname to the roster
|/
* 3a4b5c6 (origin/main, main) Add roster folder

Say

  • git fetch downloads what is on GitHub without changing your files. git pull fetches and also merges it into your branch.
  • git log --oneline --graph --decorate is the single most useful command for understanding a repo. Make everyone run it now and read it aloud.

Do

  • Ask someone to find a teammate's branch in their own graph.

Watch for

  • The output will look different for everyone. That is the point. Do not worry if it does not match the slide.
03 — Lab

Never commit your secrets

.gitignore, lives in the project root
.env
.env.local
node_modules/
__pycache__/
.venv/
.DS_Store

Anything listed in .gitignore is never committed.

If it happensIf a key reaches a public repo, treat it as stolen. Revoke it at the provider first, then clean up. Deleting the file in a new commit does not remove it from history.
  • Keys, passwords and tokens go in .env
  • .env goes in .gitignore before the first commit
  • Never paste a key into chat or a screenshot

Say

  • Automated scanners watch public GitHub for keys. A leaked key is used quickly. The fix is to revoke it, not to hide it.
  • On a hackathon team this is the Platform Captain's job to check, but everyone commits, so everyone needs to know.

Do

  • Have them create a .gitignore in hello-yourname now, add a fake .env file, and run git status to see that .env does not appear.

Watch for

  • The .gitignore only stops files that are not yet tracked. If a file was already committed, ignoring it later does not remove it. Mention it, do not dwell on it.
03 — Lab

When it goes wrong

What you seeWhat it means, and the fix
nothing to commitYou have no changes, or you forgot to save the file
rejected (non-fast-forward)Someone pushed first. Run git pull, then push again
Changes not stagedYou edited but did not git add. Run git status
I committed to the wrong branchAsk for help before you push. It is fixable
I want to undo my edits to a filegit restore FILE throws the edits away. There is no undo for that

Say

  • Most Git problems are one of these five. If you are stuck and cannot read the message, copy it exactly and ask. Do not guess commands from the internet.
  • Commands that rewrite history or delete work are on the list for later. Until then, if a Stack Overflow answer says --force, stop and ask.

Watch for

  • git restore discarding edits is permanent. Say that loudly.

Issues are your to-do list

On a hackathon team, the issue list is the plan. If it is not an issue, it is not being done.

  1. New issue, with a clear title: what, not how
  2. Describe the problem or the goal in two lines
  3. Assign it to someone. Add a label like bug or feature
  4. Reference it from a commit, or close it with Fixes #12
link work to an issue
$ git commit -m "Add roster page, refs #3"
# when the work is done, in the pull request:
Fixes #3

Say

  • From Week 3 we plan every sprint as a list of issues. Today just practice making one.
  • Good issues are small enough to finish in an hour or two. 'Build the app' is not an issue. 'Add a send button that calls the API' is.

Do

  • Everyone opens one issue in git-gym: 'Suggest a Git exercise'. It is one of the tasks.
