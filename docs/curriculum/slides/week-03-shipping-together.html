Last week — quick check
You ran git commit. Where does your snapshot live now?
A commit saves a snapshot in your local repository. It reaches GitHub only when you run git push.

Say

  • This is the single most common Git misunderstanding. If many get it wrong, redraw the four-box diagram from last week.
Last week — quick check
Your push is rejected with 'non-fast-forward'. What now?
Someone pushed first. Pull their commits into yours, then push. Forcing would overwrite their work.

Say

  • Ask: why is --force dangerous? Because it makes GitHub match your computer, and throws away whatever your teammate pushed.

How a change reaches main

The one ruleNobody pushes straight to main. Every change goes through a pull request, even when it is one line. That is what keeps main always working.

Say

  • Five steps. You have done two already: issues and branches. Today is steps three to five.
  • A pull request is a conversation about a change: here is my branch, please look at it, then merge it if it is good.

Do

  • Point at the flow while you talk, and leave it on screen.

Watch for

01 — The team loop

Anatomy of a good pull request

the template every PR starts from
## What changed
- Added a send button to the chat page

## Why
Fixes #7

## How to test
1. Open the preview link
2. Type a message, press Send
3. It appears in the list

## Screenshots
(drag an image here)
  • Small. One idea per PR. If you cannot explain it in a sentence, split it.
  • Linked. Fixes #7 closes the issue when it merges.
  • Testable. Say how someone checks it works.
  • Visual. A screenshot for anything the user sees.

Say

  • A PR is for your reviewer, not for you. They have not been inside your head for two hours. Tell them what changed, why, and how to check.
  • Small is the single biggest factor in whether a PR gets reviewed well. A 20-line PR gets read. A 600-line PR gets approved without anyone reading it.

Do

  • Open a real PR on the projector in the team repo and show where the template appears. Put the template file in .github/pull_request_template.md beforehand.

Watch for

  • Students will open PRs titled 'update' with no description. Send those back, kindly, until it becomes a habit.
01 — The team loop

Reviewing a teammate's work

  1. Read the description. What is this meant to do?
  2. Open Files changed. Read every line.
  3. Run it, from the preview link or on your machine
  4. Comment on specific lines. Then Approve or Request changes
PrefixMeans
question:I do not understand this part
nit:Tiny, optional, your call
blocking:Must change before merging
Review the code, not the person. Say what you would do, not what they did wrong.

Say

  • The prefixes matter more than they look. Without them every comment feels like a demand, and every reviewer is a bully.
  • Approving something you did not run is not reviewing. If you did not run it, say so in the comment.

Do

  • Model one review live: open a PR, add a nit, a question and a blocking comment, then approve.

Watch for

  • Shy students will approve everything without reading. Shy reviewers are the biggest risk to main. Tell them they are allowed to ask questions.
01 — The team loop

Three ways to merge, one rule for main

MethodWhat main's history looks likeUse it
Merge commitEvery branch commit kept, plus one merge commitFine, can be noisy
Squash and mergeOne tidy commit per pull requestOur default
Rebase and mergeRewrites commits onto mainSkip it for now
Protect mainIn Settings, add a rule for main: require a pull request before merging, and block force pushes. Now even you cannot break main by accident.

Say

  • Squash and merge keeps main readable: one commit per feature, with the PR title as the message. For a team of beginners it is the least surprising.
  • We skip rebase. It rewrites history, and rewriting shared history is how teams lose work.

Do

  • Show the three options on the green merge button on a real PR.

Watch for

  • Branch rules for private repositories can need a paid plan. Our repos are public so the rules are free. Check Settings, then Rules or Branches, to see what your plan allows.
02

Merge conflicts

What they are, why they are normal, and how to fix one.

Say

  • Say this clearly: a conflict is not an error. It is Git asking you a question.
02 — Merge conflicts

A conflict is a question

  • Two people changed the same lines.
  • Git cannot guess whose version is right, so it stops and asks.
  • It marks the file with <<<<<<<, ======= and >>>>>>>.
  • You pick, remove the markers, and commit.
Why this mattersConflicts are boring when you know what they are, and terrifying when you do not. By the end of today you will know.

Say

  • The markers: the top half, between the first two lines, is your version. The bottom half is the other person's. Your job is to produce the one version that is correct.
  • Sometimes that is yours, sometimes theirs, sometimes both combined. It is a decision, not a click.

Watch for

  • Do not use the word 'error'. Use 'question'. It changes how they feel about it.
02 — Merge conflicts

Resolve one

This is what VS Code shows. Try each button and read what it says.

Say

  • Click all three. 'Accept both' is the dangerous one: it keeps both lines, and here that means the file sets the name twice.
  • After resolving: save, run the app to check it still works, then git add and git commit. People forget to test, and ship a file that no longer runs.

Do

  • Ask the room which button is right here. There is no right answer without knowing which name the team wants. That is the point.
02 — Merge conflicts

Avoiding most conflicts

  • Small pull requests, merged quickly. A branch that lives for a day conflicts less than one that lives for a week.
  • Pull from main often, into your branch, so you resolve small differences early.
  • Split the work by file. Interface people in the interface files, API people in theirs.
  • Say it out loud: 'I am editing the header'. Ten seconds in chat saves ten minutes.
  • Do not reformat whole files. Auto-formatting touches every line and conflicts with everyone.

Say

  • You will still get conflicts. That is fine. The goal is to make them small.
  • Generated files such as lockfiles are the exception: do not hand-merge them. Delete them, regenerate them, commit the result. We will meet one in the AI weeks.

Lab: conflict on purpose

Teams of three. You will create a conflict and then fix it.

Say

  • Seventeen minutes. Teams of three, one laptop each. Do not split the steps between you, everyone does everything.
03 — Lab

Make a conflict, then fix it

  1. Each person: git switch -c motto-yourname
  2. Each edits line 1 of team-motto.md, differently, and pushes
  3. Person A opens a PR and merges it
  4. Person B opens a PR: GitHub says This branch has conflicts
  5. Person B: pull main into the branch, then resolve in VS Code
  6. Commit, push. The PR can now merge. Then Person C
what Person B does
$ git switch motto-yourname
$ git pull origin main
Auto-merging team-motto.md
CONFLICT (content): Merge conflict in team-motto.md
Automatic merge failed; fix conflicts and then commit the result.
# open team-motto.md, keep the right lines, remove the markers
$ git add team-motto.md
$ git commit -m "Resolve merge conflict in team motto"
$ git push

Say

  • The repo is conflict-lab. Everyone edits the same line of the same file, which is the cause of every conflict.
  • When the second PR shows 'This branch has conflicts', that is the lesson. Celebrate it. Then fix it.

Do

  • Walk the teams. The usual traps: leaving the <<<<<<< markers in the file, resolving and forgetting git add, and resolving on main instead of the branch.
  • Ask each Person B to read the result aloud before pushing. Make them check the markers are gone.

Watch for

  • git pull origin main merges main into the current branch. It is the one command here they have not used. Say what it does before they run it.
  • If a team gets truly stuck, git merge --abort returns the branch to how it was. Say it once and keep it in your pocket.
03 — Lab

The board and the daily standup

  1. In the team repo, create a Project (board view)
  2. Columns: Todo, In progress, In review, Done
  3. Move your card when you start, and when you open the PR
  4. Standup: what did I finish, what am I doing, what is blocking me
Why a standupOn hackathon day, run a five-minute standup every three hours. It catches the person who has been stuck for two of them.

Say

  • The board is just issues arranged in columns. Its only job is to show, at a glance, who is doing what and what is waiting for a review.
  • Reviews are the usual bottleneck. If the 'In review' column is full, the team's job is to review, not to start new things.

Do

  • Create the board together on the projector, then let teams build their own.
03 — Lab

Mini sprint: three issues, three PRs

  1. Each team agrees a tiny pretend product: a team page
  2. Write three issues, one per person, each about 15 minutes of work
  3. Everyone: branch, change, push, open a PR using the template
  4. Review someone else's. Nobody merges their own
  5. Squash and merge all three. Move the cards to Done
The rulesRules for the sprint: main only changes through a PR. Every PR gets one review. If two PRs touch the same file, talk first.
What you leave withYou will finish with a board, three merged PRs and a git history you can read.

Say

  • This is a rehearsal of the real thing. Same rules as hackathon day. If it feels slow, that is correct. It gets fast with practice.
  • Watch for the team where one person does everything. That is a signal, write it down, and ask them to hand a task over.

Do

  • Float between teams. The things to check: are PRs small, do they have descriptions, is someone actually reviewing?
  • Take note of who reads code carefully, who communicates, who finishes. You need it for the role board in Week 7.

Watch for

  • Teams will want to build a real feature. Keep it tiny. The topic is the workflow, not the page.
